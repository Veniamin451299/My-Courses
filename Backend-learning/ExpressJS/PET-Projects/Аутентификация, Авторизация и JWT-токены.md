Сейчас наш Task Manager «общий»: любой человек может зайти и увидеть все задачи. В реальном продакшене у каждого пользователя должен быть свой личный аккаунт. Каждый должен видеть, создавать и удалять **только свои собственные задачи**.

Чтобы это реализовать, нам нужно пройти через 3 инженерных шага:

1. **Регистрация**: Сохранение пользователя в БД и **хеширование** пароля.
2. **Аутентификация (Вход)**: Проверка пароля и генерация **JWT-токена**.
3. **Авторизация (Защита роутов)**: Мидлварь, которая проверяет токен и понимает, какой именно пользователь делает запрос.

Давай разберем теорию, а код для пэт-проекта ты напишешь сам на основе моих архитектурных подсказок.

# Шаг 1. Безопасное хранение паролей (`bcrypt`)

**Закон бэкенда:** Никогда не храни пароли в базе данных в открытом виде. Если хакер украдет базу, он получит пароли всех пользователей.  
Мы используем библиотеку **`bcrypt`**. Она превращает пароль `123456` в длинную нечитаемую строку (хеш): `$2b$10$XyZ...`. Этот процесс необратим — из хеша нельзя вернуть пароль. При входе пользователя `bcrypt` просто заново берет введенный пароль, хеширует его тем же способом и сравнивает два хеша.

Как это работает (Теория):
`npm install bcrypt`

```javascript
const bcrypt = require('bcrypt');

// При регистрации (Хешируем пароль)
const hashedPassword = await bcrypt.hash('пароль_пользователя', 10); // 10 — уровень сложности

// При входе (Сравниваем введенный пароль с хешем из БД)
const isMatch = await bcrypt.compare('введенный_пароль', hashedPassword); // true или false
```

# Шаг 2. Что такое JWT (JSON Web Token)?

Когда пользователь успешно вошел (ввел правильный логин и пароль), сервер не должен заставлять его вводить пароль при каждом клике на сайте. Сервер выдает ему «паспорт» — **JWT-токен**.

**JWT** — это длинная строка из трех частей, разделенных точками: `header.payload.signature`.
- **Payload (Полезная нагрузка)**: Внутри токена зашифрованы базовые данные пользователя, например, его `userId`. Хакер может прочитать этот payload (он просто закодирован в base64).
- **Signature (Подпись)**: Это самая важная часть. Сервер подписывает этот токен своей секретной солью из файла `.env` (`JWT_SECRET`). Если хакер попытается изменить `userId` внутри токена, подпись станет невалидной, и сервер сразу поймет, что токен подделан.

Как это работает (Теория):
`npm install jsonwebtoken`

```javascript
const jwt = require('jsonwebtoken');

// 1. Создаем (генерируем) токен при логине
const token = jwt.sign(
  { userId: 1 }, // Payload (что прячем внутри)
  process.env.JWT_SECRET, // Секретный ключ сервера
  { expiresIn: '24h' } // Время жизни токена
);

// 2. Проверяем токен в мидлваре авторизации
try {
  const decoded = jwt.verify(token, process.env.JWT_SECRET);
  console.log(decoded.userId); // Получаем id пользователя, если токен валидный
} catch (err) {
  // Токен протух или подделан
}
```

# Шаг 3. Изменение схемы базы данных (Prisma)

Чтобы связать Пользователей и Задачи связью **«Один ко многим»** (у одного пользователя может быть много задач, но у каждой задачи есть только один автор), нам нужно обновить файл `schema.prisma`.

```prisma
model User {
  id       Int    @id @default(autoincrement())
  email    String @unique
  password String
  tasks    Task[] // Ссылка на массив задач пользователя
}

model Task {
  id          Int      @id @default(autoincrement())
  title       String
  description String?
  isCompleted Boolean  @default(false)
  createdAt   DateTime @default(now())
  
  // 🌟 Добавляем связь с пользователем
  userId      Int
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

_После изменения схемы не забудь запустить миграцию: `npx prisma migrate dev --name add_user_relation`._

# Архитектурный план: Твое ТЗ на внедрение JWT

Давай разделим эту огромную задачу на части. Сейчас мы напишем **только слой работы с пользователями (Auth)**.
1. **База данных**: Обнови свой файл `schema.prisma` (как в примере выше) и запусти миграцию.
2. **Переменные окружения**: Добавь в `.env` строку `JWT_SECRET="твое_очень_секретное_слово"`.
3. **Регистрация (`POST /api/auth/register`)**:
    - Создай схему валидации Zod для пользователя (`email` и `password` минимум 6 символов).
    - В `authService` проверь через Prisma, нет ли уже пользователя с таким `email`. Если есть — кидай ошибку `400 BadRequestError` ("Email уже занят").
    - Хешируй пароль через `bcrypt.hash`.
    - Сохрани пользователя в БД.
4. **Вход (`POST /api/auth/login`)**:
    - Найди пользователя в БД по `email`. Если не найден — кидай ошибку `401 UnauthorizedError` ("Неверный email или пароль").
    - Сравни пароли через `bcrypt.compare`. Если не совпали — кидай `401`.
    - Если всё супер — сгенерируй JWT-токен через `jwt.sign` и верни его клиенту в формате `{ status: "success", token: "..." }`.

Напиши для этой логики файлы `authRouter.js`, `authController.js` и `authService.js`. Задачи (`toDoRouter` и контроллеры) пока не трогай, их мы защитим на следующем шаге с помощью кастомной мидлвари!
